## 1. 设计目标

把 ADR-0006 §C（决策 5 判定权拆分）与 §D（决策 6 机械漂移检查 J-1~J-4）从**文字判据**落成**一条可复算命令**，并在归属上守死一条线：**判据与生成器归本仓，判定表本体归消费仓**。

## 2. 设计依据

### 2.1 调研结论

| 调研发现 | 设计决策 | 引用 |
|---------|---------|------|
| J-1~J-4 全为确定性可核（零 LLM 判断） | 以单脚本 + `git` 子命令实现，纯机械 exit code | RESEARCH §4.1-1 |
| 手记残余 3 天两处漂移 | 判据不落文字，落**可复算命令**；读数每次现取 | RESEARCH §3.5 |
| 决策 5 表归消费仓 | 本仓只提供**三列格式 + 骨架生成器**，绝不代填代判 | RESEARCH §4.1-3 |
| J-1 的「指针」与「入库」是两个事实 | 同一函数内一次判定两事实（不得拆两处，防退化为单一 grep） | RESEARCH §4.1-4 |
| 既有先例 `verify-anchor` 已验证同方法可行 | 复用其形态：只读、零副作用、显式 exit 语义 | RESEARCH §4.2 |

## 3. 架构设计

### 3.1 整体架构

```
                 Spec_Workflow（权威源侧，本仓）
                 ├─ scripts/downstream_compliance.py  ← 本 feature 唯一交付物
                 │     ├─ CONSUMERS 登记常量（消费仓 / 副本 / 判定表路径 / 回流窗）
                 │     ├─ check_consumer(): J-1 / J-2 / J-3 / J-4 四判据
                 │     └─ emit_table(): 三列骨架 → stdout
                 └─ 权威源文件（只读）：docs/ASSERTION_EVIDENCE_FRAMEWORK.md
                                        docs/007_hallucination_audit_asymmetric_evidence.md
                                    │
                                    │  只读（git 子命令 + 文本读取）
                                    ▼
                 消费仓（如 F:\Cpp_Hub）
                 ├─ 副本文件（指针 + 冻结版本）
                 ├─ .git / origin（推送状态、回流提交）
                 └─ docs/COMPLIANCE_TABLE.md（判定表 —— 归该仓，本仓只读）
```

### 3.2 模块划分

| 模块 | 职责 | 输入 | 输出 | 依赖 |
|------|------|------|------|------|
| `CONSUMERS` | 消费仓登记（含副本↔权威源配对、判定表路径、回流窗） | — | 常量表 | 无 |
| `_git()` | 统一 git 调用（`-C` 定仓、返回 rc+stdout） | root + args | `(rc, stdout)` | 本机 `git` |
| `is_excluded` 同族：`_frozen_version` / `_authority_version` | 版本行解析（副本侧含「冻结于」优先；权威侧取头部 `version`） | 文件文本 | 版本串或 `None` | 无 |
| `check_consumer()` | 逐判据读数与判定（**J-1 两事实同函数内一次判定**） | 消费仓登记 | `(rows, blocking, structural)` | `_git` |
| `emit_table()` | 三列骨架生成（**只写 stdout**） | `CONSUMERS` + 权威源版本 | markdown | 无 |

### 3.3 数据流

1. 遍历 `CONSUMERS` → 对每仓调用 `check_consumer()`；
2. 每判据产出一行读数 `(判据, 对象, 读数, 判定)`；
3. 判定分两档：`blocking`（已判且不满足 → exit 1）/ `structural`（无法判定 → exit 2）；
4. `main()` 聚合打印，**blocking 优先于 structural** 返回。

### 3.4 控制流

`main()` → `--emit-table` 分支（直接返回 0）或全量检查分支 → 遍历消费仓 → 打印读数块 → 依 blocking/structural 返回 0/1/2。

## 4. 接口定义

### 4.1 命令行接口

```
python scripts/downstream_compliance.py                 # J-1~J-4 全量
python scripts/downstream_compliance.py --emit-table     # 判定表三列骨架（stdout）
```

exit：`0` 全部满足 / `1` 有阻塞项（指针缺失/未入库、版本差异未记录）/ `2` 结构性异常（消费仓不可达、非 git 仓、版本行解析不全、判定表缺失）。

### 4.2 消费仓登记项（`CONSUMERS` 元素）

```python
{
  "name": str,          # 消费仓名（仅展示与报错用）
  "root": str,          # 消费仓绝对路径
  "branch": str,        # 比对 origin 的分支名（J-2）
  "table":  str,        # 判定表相对路径（归该仓）
  "copies": [{"path": str, "authority": str}],   # 副本 ↔ 权威源配对
  "reflux_since": str,  # J-4 观测窗起点——**须为含时区的完整时刻**（如 "2026-08-17
                        # 00:00:00 +0800"）。裸日期会被 git approxidate 以**当前时钟**
                        # 补齐时刻 ⇒ 截止点随执行时刻漂移、读数不可复算（实测 39/36/35）
  "reflux_pattern": str # J-4 回流标记 grep 模式（**须配 `-E`**：BRE 下 `|` 是字面量）
}
```

## 5. ADR-0010 三问门禁

| 问 | 答 | 依据 |
|---|---|---|
| **Q1 放哪层** | **Layer-1**（独立脚本，非 hook、非校验器） | ADR-0006 §D 明示 J-1~J-4 为「纪律 + 可复算命令」，不进三校验器 |
| **Q2 激活条件** | **已激活**（用户指令「ADR-0006决策accepted 然后开始实现」= 决策 5/6 转 accepted 即触发落地） | ADR-0006 §C/§D 2026-09-26 accepted |
| **Q3 未激活副作用** | **0**——本脚本不被任何 hook 调用，不进 pre-commit；不调用即零副作用、零运行时开销 | I-2 只读不变式 |

## 6. 替代方案

### 6.1 方案 A：登记常量 + 单脚本（**选择**）

- 描述：消费仓以脚本内 `CONSUMERS` 常量登记；判据与生成器同文件
- 优点：零新数据文件、零依赖；登记面小且可 code-review；跨仓只读无写面
- 缺点：新增消费仓需改代码（非纯配置）；路径硬编码跨机不可用
- 选择理由：当前消费仓**仅 1 个**（Cpp_Hub），配置外置的收益为零而引入新文件面；跨机风险由「不可达 → exit 2 显式提示」兜住（I-3）

### 6.2 方案 B：判据接进 pre-commit 门禁（**否决**）

- 描述：把 J-1~J-4 做成第 6 个 hook，提交即阻断
- 否决理由：**直接违 ADR-0006 §D**（J-1~J-4 定位为「纪律 + 可复算命令」，非门禁）；且判据依赖**另一仓**的可达性（Cpp_Hub 不在则每次提交必失败），把外部环境不确定性引入本仓门禁 = 制造脆弱门禁

### 6.3 方案 C：判定表本体落在本仓（**否决**）

- 描述：在本仓建 `docs/COMPLIANCE_TABLE.md`，代所有消费仓集中记账
- 否决理由：**违决策 5 的归属规则**（判定权在消费仓；SLSA "in the eye of the beholder" 明许委托但**须显式**——集中代持即把「委托」变成「替代」，正是 ADR-0006 §E 明确不采纳的方案 C 的变体）

### 6.4 方案 D：外部配置 + JSON 登记表（**否决**）

- 描述：消费仓登记外置为 `tools/` 下 JSON 文件，脚本读取
- 否决理由：引入新数据文件与「配置与实现分离」的漂移面（本仓已多次实证配置漂移）；当前登记面（1 仓 / 2 副本）不足以摊销该复杂度

## 7. 错误处理

| 错误场景 | 处理方式 | 用户可见信息 |
|---------|---------|------------|
| 消费仓路径不存在 | `structural` → exit 2 | `消费仓不可达: <root>` |
| 消费仓非 git 仓 / 无 remote | `structural`（J-2 / J-4）→ exit 2 | `无法比对 origin/<b>` / `git log 失败` |
| 副本文件不存在 | `blocking`（J-1）→ exit 1 | `副本不存在` |
| 副本有指针但未入库 | `blocking`（J-1）→ exit 1 | `指针未入库` |
| 版本行解析不全 | `structural`（J-3）→ exit 2 | `版本行解析不全` |
| 版本有差异但判定表缺失 | **不报 blocking**，标 `— 无判定表（待消费仓落盘）` + `structural` | 差异量照打印 |
| 版本有差异且判定表存在但未记录该副本 | `blocking`（J-3）→ exit 1 | `差异未记录` |

## 8. 不变式（Invariants）

1. **I-1 单点判定**：J-1 的「指针存在」与「已入库」两事实在**同一函数内一次判定**，不得拆为两处实现（防退化为单一 grep —— 重审 #1 的错误形态）。
2. **I-2 只读**：不对消费仓写任何文件；`--emit-table` **只写 stdout**。全程零写入。
3. **I-3 显式失败**：不可判定的场景一律走 `structural` 并显式打印，**绝不静默通过**。
4. **I-4 零第三方依赖**：stdlib + 本机 `git`；无网络调用。
5. **I-5 表归消费仓**：本仓不创建、不修改、不代持任何消费仓的判定表。

## 10. 对实施的输入

### 10.1 关键工程约束

- 单文件、stdlib only、无 hook 注册（不碰 `.pre-commit-config.yaml`）
- `CONSUMERS` 为唯一登记面；新增消费仓 = 加一条
- 版本行解析只取头部窗口（前 N 行），避免正文误命中

### 10.2 风险与缓解

| 风险 | 缓解 |
|------|------|
| 路径硬编码致跨机不可用 | 不可达即 `structural` exit 2 显式提示（I-3），不静默通过 |
| 判定表长期不落盘 → J-3 永远「无表」 | 标 `— 待消费仓落盘` 并在 `--emit-table` 提供可交付骨架；登记 H2 待首填复核 |
| 判据集不足（H1） | 首轮实跑后评估是否需 J-5（结构化差异），登记不改本批设计 |
