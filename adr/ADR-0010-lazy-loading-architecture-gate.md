## 背景（Context）

### 1. 懒加载思想的原始设计（用户提出，坚持为框架架构思路）

2026-09-08 会话中用户明确：**懒加载不是 P-019 的临时候选，而是本框架需要实现的架构思路**。原始设计约束（会话产出）：

- **Layer-0 文档层**：自足可读——纯文档消费者（阅读者 / M7 审计 / 外部 reviewer）零工具依赖即可完整使用框架
- **Layer-1 工具层**：按需激活——每个工具/服务独立封装，未激活即"不存在"
- **单向依赖**：Layer-1 依赖 Layer-0；Layer-0 绝不反向依赖 Layer-1
- **激活零副作用**：激活动作不污染文档层、不改写既有工具、引入后续无隐式负担

### 2. 被 P-019 实施批次误读的教训

P-019 RESEARCH v1.0 曾把懒加载列为 C2 候选（RUNNER 存在性探测，~15 行小改不触 runner 本体），v1.1 用户裁决改为并入后将其降级为"并入前过渡机制"，并在并入完成后自然退役——这是**具体实现层面的退役**，不是**架构原则层面的废止**。本次澄清：两者应严格分置。

### 3. 社区候选池（P-018）的量级——过重风险的真实来源

COMMUNITY_ECOSYSTEM_RESEARCH v1.2 候选池（§3/§4）：

| 候选 | 形态 | 激活机制 | 未激活成本 |
|------|------|---------|-----------|
| AGENTS.md 桥 | 文件（Layer-0） | 生成即存在 | 零 |
| drift-gate 概念 | 仅登记（repo_stats 演进候选） | 计模式版本时 | 零 |
| **step-gate / P-020 决策产物管线** | 扩展 spec_runner（Layer-1） | 独立 feature 裁决 | 零（不实现即不存在） |
| ARC 轻量先导 | 外部 CLI（Layer-1） | 触发驱动（dsh H2） | 零 |
| DeepEval 评测臂 | pytest 依赖（Layer-1） | 首轮评测后裁决 | 零 |
| gpt-researcher / Gigaxity MCP | 外部服务（Layer-1） | H4 服务形态实测 | 零 |
| ADR 三层 enforcement | 模式吸收 | 登记候选 | 零 |

**关键观察**：候选池治理机制（"触发驱动不排队"+ "服务形态非库依赖"+ "试点再升级"）**已是懒加载思想的不自觉实例**——只是未贴标签、未成制度。缺制度化 = 每个候选接入时口头重争边界，零依赖 D6 只挡"第三方依赖"，挡不住"本仓自己长胖"。

## 决策（Decision，accepted 2026-09-08）

**将懒加载升格为强制的第三吸收门禁**（与零依赖 D6 互补：D6 管外部依赖引入，懒加载管内部结构生长；与 P-009 D1 的 L1-L7 分层约束分工：L1-L7 约束 spec_runner 自身模块结构，本门禁约束**候选吸收的准入边界**，两者作用对象不同、不构成制度重复）：

> 任何候选吸收（社区框架 / skill / MCP / 外部服务 / 本仓新增工具）前，强制回答三问：
> 1. **放哪层？** Layer-0（纯文档/文件）还是 Layer-1（工具/服务）？
> 2. **激活条件？** 什么触发它从"登记"变"实现"？无触发即不实现（触发驱动不排队）
> 3. **未激活副作用 = 0？** 不 import / 不启动 / 不扫描 / 文档层无感知（Layer-1 单向依赖 Layer-0）

判定：三问通过 → 进候选池；**未激活零副作用不成立** → 直接否决（如引入重依赖的 Langfuse：按 D6 零依赖先例否决，见 §4 备选 A 记录）。

> **边界声明（2026-09-08 消歧）**: 本门禁的适用对象 = **候选吸收物**（社区框架 / skill / MCP / 外部服务 / 本仓新增工具——即提案中列出的、有待引入的具体事物），**不适用 = 调研报告/提案文档本体**（如 COMMUNITY_ECOSYSTEM_RESEARCH.md 这类生成端调研产物，属 Layer-0 文档，质量由 Step 2 Review / 独立 pass 管辖）。启发式：被三问审问的是"引入什么"（候选物），不是"提案怎么写"（报告文档）。调研报告本身是候选清单的载体而非候选本身。

**适用位点（3 处）**：
- SPEC_PROCESS 吸收/并入裁决（Step 2 调研收束处的候选判定）
- 候选池维护（community-ecosystem §4 编辑时逐项复核）
- tools/ 目录新增条目（repo_stats 模式库对账时核对分层归属）

## 考虑的替代方案（Alternatives Considered）

### 方案 A：不引入，维持当前候选治理（否决）

- 优点：零结构新增
- 缺点：候选池治理机制已是"不自觉懒加载"，但不命名 = 边界不可继承、不可审查、不可机械化对账；下一候选接入（如 P-020 step-gate 或 ARC）仍需重新口头论证"为什么这个可以、那个不行"
- 否决理由：与"吸收扩散风险随候选池增长"的现实冲突——候选越多，无制度化的边界争议越多

### 方案 B：仅登记为方法论注记（不强制）（否决）

- 优点：比 A 多一步文本承认
- 缺点："注记"无机械/流程位点，等价回到口头纪律；本框架证据表明非机械化的纪律（如 DEV-LOG 三重要求）必须靠 review 臂持续看守，成本更高
- 否决理由：半途而废——要么升格为门禁，要么不加（与既有无极禁用 off/on 二态的取舍模式一致）

### 方案 C：懒加载门禁（选择）

- 描述：如决策节。三问中 Q1（分层归属）/Q2（激活条件）可机械回答，Q3（未激活零副作用）为**弱否定标准**（本仓内无足迹可验证，但无法由生成端严格证明）——作为准入可操作标准而非机械证明
- 优点：① 候选接入决策从"口头重争"变"三问答录"；② 与 D6 互补形成完整防过重双闸（外部依赖 + 内部生长）；③ 既有判例（Langfuse 按 D6 否认、gpt-researcher MCP 形态、ARC 试先导、ADR 三层纯模式）与三问判定一致，无历史推翻（P1-1 修正后论证成立）
- 缺点：新增一处流程判定动作（吸收裁决时多答三问，~30 秒）；Q3 存在判定边界（见负面节）
- 缓解：三问嵌进既有裁决表（不新增流程步骤声明，仅多一列/多一行）；Q3 判定标准显式化（未激活时本仓内无任何代码/扫描/配置足迹）

### 方案 D：全量落地懒加载执行件（Layer-0/Layer-1 代码层强制）（暂缓）

- 描述：把分层做成代码/构建层强制（如工具独立进程 + 显式激活注册表 + 扫描器验收）
- 优点：机械化最强
- 缺点：本仓工具规模（4 可执行件 + runner = 5）远未到需要运行时强制分层的量级——YAGNI；先以门禁文本约束，工具数量跨过阈值（如 >8 可执行件）再评估执行件落地。阈值 8 派生理据：当前 5 件全量显式激活仍可机械维护；增量候选池（ARC/DeepEval/调研链 MCP/ADR 三层 ≥4 件）跨过 8 后配对复杂度（Σ 激活×交互）进入需要注册表管控的量级
- 处置：登记为失效条件触发项（见验证节）

## 后果（Consequences）

### 正面

- 候选治理从"触发驱动不排队"的口头纪律 → 三问可答录的显式门禁，防过重有了机械可审查边界
- 与 P-019 C2 不冲突：C2 退役的是"RUNNER 探测"具体实现；本 ADR 升格的是垂直向（Layer-0/Layer-1）架构约束（见关系辨析）
- 既有先例零推翻：Langfuse（重依赖违反 D6 零依赖 → 否决）、gpt-researcher（MCP 服务形态未激活零成本 → 候选）、ARC（不吸收运行时 → 候选）、ADR 三层（纯模式 → 候选）——与三问判定一致

### 负面

- 新增一处裁决动作（吸收时答三问）
- "未激活零副作用"的机械判定边界：部分候选难以证明绝对零副作用（如外部服务未来接入端点）——缓解：判定标准 = 未激活时本仓内无任何代码/扫描/配置足迹，端点依赖属激活后的运行态

### 中性 / 后续行动

- P-020 落地时以首例完整执行三问（放 Layer-1 / 激活=独立 feature 裁决 / 未激活零副作用）
- docs/adr README 索引登记本 ADR
- 若未来实施方案 D（执行件强制），本 ADR 追加 D 状态追记

| 维度 | P-019 C2（2026-09-08 已退役） | 本 ADR（垂直架构约束） |
